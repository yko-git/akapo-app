# 0002-Feature-based

Feature-based 採用

## 適用範囲

本プロジェクトのフロントエンドにおける機能別設計に適用する

## 背景

拡張性・可読性を高めるため、機能ごとの整理が必要

### 必要な理由

- 機能に関するコンポーネント・hooks・サービス・型定義がバラバラになっている
- その結果、複数のフォルダを横断することになり、可読性が低く、構造の崩れが起きやすい

## 選択肢

- Clean Architecture
  - 外から内にのみの依存関係を守る
  - 「1つの関心は1つの責任」＝変更に強い
  - フォルダ構造は自由
  - 中〜大規模、長期保守プロジェクト向き

- Feature-based
  - 依存関係は UI → hooks → model → API
  - 機能単位でフォルダを分ける
  - 機能ごとに責任分界が明確になり、他機能との干渉を減らせる
  - 小〜中規模プロジェクト向き

- Feature-sliced
  - 依存関係は pages → features → entities → shared
  - 機能単位でフォルダを分ける
  - 各レイヤーに明確な責務を持たせる
  - 機能+レイヤー構造+依存ルールまで定義された設計（Feature-basedはざっくり機能ごとに分けている）
  - 大規模、長期保守プロジェクト向き
  - 初期構築が重い

## 決定

Feature-basedを採用

## 理由

- 機能ごとに関連コードを集約でき、変更影響範囲を把握しやすい
- hooks・components・api・types を同じ機能配下で管理でき、可読性を維持しやすい
- 小〜中規模の個人開発において、過度な設計コストを避けられる
- 将来的な機能追加時も、責務単位で拡張しやすい
- チーム開発時にも、機能単位で作業分担しやすい

## トレードオフ

- Feature-Sliced のような厳密な依存ルールは持たない
- 運用ルールを決めないと、feature 間依存が複雑化する可能性がある
- 大規模化した場合、責務境界が曖昧になる可能性がある
