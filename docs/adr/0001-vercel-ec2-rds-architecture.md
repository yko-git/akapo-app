# 0001-vercel-ec2-rds-architecture

Vercel + EC2 + RDS採用理由

## 適用範囲

本プロジェクトのインフラ・デプロイ構成に適用する

## 背景

認証付きAPIを前提としたフロントエンド・バックエンド分離構成を採用し、将来的な機能追加や保守を考慮したインフラ構成が必要

### 必要な理由

フロントエンドとバックエンドを分離した構成で、
認証付きAPIを前提としたWebアプリケーションを構築したい。

また、学習目的として以下を経験したい。

- フロントエンド / バックエンド分離構成
- APIサーバ運用
- AWSインフラ構築
- CI/CD
- クラウドサービス連携

## 選択肢

- Vercel + EC2 + RDS
  - Frontend / Backend の責務分離がしやすい
  - Next.js と Vercel の親和性が高い
  - EC2 により Linux / Node.js サーバ運用を学習できる
  - RDS により DB 運用負荷を軽減できる
  - AWSサービス連携を実践的に経験できる
- Vercel + Supabase
  - フロントエンドをVercelに配置
  - バックエンド/DBをSupabaseに集約
  - バックエンドのインフラ管理が不要＝インフラ学習の幅が限定される
- AWS ECS / Lambda 構成
  - スケーラビリティが高い
  - モダンなAWS構成を学習できる
  - 個人開発規模ではオーバースペックになりやすい
  - 学習コストが高い

### フロントエンド / バックエンド分離構成のメリット

- UI とビジネスロジックの責務分離が明確になる
- Frontend / Backend を独立して開発・デプロイできる
- API中心設計となり、疎結合な構成を維持しやすい
- 将来的なモバイル対応や他クライアント追加に対応しやすい
- 実務に近い構成を学習できる

## 決定

Vercel + EC2 + RDSを採用

## 理由

- APIサーバの構築・運用経験を得たい
- Next.jsとVercelの相性が良いため、フロントエンドの開発速度を維持できる
- RDSを利用することでDBの可用性・バックアップ管理を簡略化できる

## トレードオフ

- サーバ管理・セキュリティ対応などの運用負荷が発生する
- Supabaseと比較すると初期構築コストが高い
- インフラ構成が分散し、管理対象が増える
